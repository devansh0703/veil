### Findings

**AR1 — CRITICAL (confidence: 9/10).** `docs/designs/veil-agent-payments.md`, Free-tier stack table: the plan lists x402 SDK + reference sample and never names the confidential-transfer JS client. The integration guide names the actual stack: **`@solana-program/token-2022`** for instructions/state/key-derivation/helpers, **`@solana/zk-sdk`** (WASM) for proof generation, **`@solana-program/zk-elgamal-proof`** for verification instructions. Meanwhile `@solana/spl-token` "has virtually no support for any of the Confidential Transfer instructions or any of the relevant types." **Impact:** the merchant SDK's "one line" and the agent SDK's proof path both hang off the wrong package if the implementer reaches for the familiar one. The fix is not extra work; it is naming the right dependency spine in the plan so the day-1 spike starts from the helper, not from scratch. **Remedy:** the plan's stack table names `@solana-program/token-2022` + `@solana/zk-sdk` explicitly, and the day-1 spike imports `deriveConfidentialKeys` from `@solana-program/token-2022/confidential`.

**AR2 — CRITICAL (confidence: 8/10).** The plan's graph layer creates "a one-time deposit address ... per payment." But the integration guide states: "Configuring normally requires the account owner to sign and supply a proof that they own the ElGamal public key being set on the account ... it cannot configure the confidential extension on the user's behalf without that signature." A one-time receiving account **must be configured before it can accept a confidential transfer**, and configuring needs the merchant (the owner) to sign a proof. Deriving a fresh address per payment and configuring it on the fly is therefore not viable: the merchant's signing key would have to be online for every payment, and a proof per account is a per-payment cost. **This is the deepest hole in the plan and neither prior review caught it.** **Remedy:** pre-create and pre-configure a **pool of N receiving accounts** (the merchant configures N up front, signing once per account, or once via the registry path if a Rust helper is acceptable), then assign one pool account per payment and recycle it after the transfer lands and the balance is swept. Register each assigned account in the merchant's derivation index so address→alias still resolves without the facilitator. This preserves the graph claim (each payment still lands at a fresh, unlinkable address from the buyer's side) while removing the per-account owner signature from the hot path. **Alternative considered and rejected:** the ElGamal registry (`ConfigureAccountWithRegistry`, no owner signature at configure time) — the guide explicitly says JS helpers for it "are not available yet," so it breaks the JS wedge.
> **Prior learning applied: `negative-privacy-claims-need-programmatic-assertion`** — the pool must be asserted pre-configured, or a fresh unconfigured account accepts nothing and the demo silently degrades.

**AR3 — HIGH (confidence: 8/10).** The CEO review recommended `DisableNonConfidentialCredits` (A6); the integration guide confirms the underlying account fields are **`allow_confidential_credits` / `allow_non_confidential_credits`**. **Remedy:** name both flags in the plan, set `allow_confidential_credits=true` and `allow_non_confidential_credits=false` on every pool account and every buyer account at configure time, and let the on-chain account reject a public credit rather than relying on application discipline. This closes the "silent public fallback" class at the source (the CEO review's A5).

**AR4 — MEDIUM (confidence: 7/10).** The integration guide: "Confidential transfers have historically spanned a few dependent transactions because the proofs exceeded the transaction size limit. **The transaction v1 format raises that limit, which lets a confidential transfer execute in a single onchain transaction.**" This changes the settlement RPC budget (Section 4) and the atomicity story. **Remedy:** decide tx-v1 vs legacy multi-tx explicitly on day 1; if the JS helper already sequences a single v1 transaction, the payment flow is one confirmation, which simplifies `verifyInclusion`.

**AR5 — HIGH (confidence: 8/10).** The plan treats "the derivation seed" as the single sensitive secret (CEO review S5). The integration guide shows there are **two independent key materials**:
1. **Confidential keys** — ElGamal keypair + AES key, derived from a wallet signature over `"solana-conf-bal/v1"` via `deriveConfidentialKeys({signer})`. Recoverable from the wallet; a signing-key-equivalent secret ("treat a request to sign the derivation message like unlocking a private view of the user's balances").
2. **The graph derivation seed** — our own scheme, not recoverable, the thing that resolves address→alias.
**Impact:** merging their lifecycles in the plan invites storing the confidential keys when they should be derived on demand, and under-protects the graph seed (which is the genuinely unrecoverable one). **Remedy:** document the two separately; derive confidential keys on demand and never store them; keep only the graph seed at rest (`0600`, merchant-only).

**AR6 — HIGH (confidence: 8/10).** The auditor key is a **global** ElGamal key per mint (`auditor: an optional global ElGamal key on the mint`). The CEO review's S1 remedy is correct: per-merchant reconciliation decrypts the **recipient ciphertext** (via the AES `decryptable_available_balance`, constant time). The auditor key is a third-party compliance feature only. **Remaining decision — mint topology (T-4):** with the demo's "2 merchants," a shared test-dollar mint plus recipient-side decryption is correct and the auditor key is unused on the critical path. If the plan enables an auditor key "for the demo," it must not also claim per-merchant privacy on a shared authenticated ledger without qualification. **Remedy:** the demo uses a shared mint, no auditor key on the hot path, and the submission states that mint-per-merchant is the multi-tenant hardening step (T-4).

**AR7 — HIGH (confidence: 8/10).** The settlement invariant "served at most once per successful payment" needs an **atomic claim**, not a read-then-write. The CEO review mapped the violation (two concurrent verifications both serve). **Remedy:** `claimServe(pid)` is a single conditional write (`VERIFYING → SERVED`), and the same transaction that flips the state is the one that authorizes serving. This is the interface the implementer must build first in the facilitator.

**AR8 — MEDIUM (confidence: 8/10).** Derivation must be one implementation. Two SDKs deriving "the same" address by two code paths is the DRY violation that silently leaks the graph. **Remedy:** a single `@veil/derive` package with one exported `derivePaymentAccount(merchantAliasPubkey, buyerPubkey, nonce)` consumed by both SDKs, property-tested for agreement (Section 3).

**Single points of failure.** (1) The facilitator — if it is down, every wrapped merchant 402s and never serves; the failure mode must be "refuse, never serve unverified," surfaced as a visible error. (2) The merchant's graph seed — unrecoverable. (3) The pre-configured pool — if exhausted, payments must queue or refuse, never fall back to a public account (AR3 makes that impossible on-chain, which is the point).

**One realistic production failure, per new path.** Merchant process restarts between payment and serve. The agent paid, the resource was never delivered, x402 has no refund. **Product answer (required):** the payment id is credited; a retry with the same id serves once the process is back; the dashboard shows a "paid, not delivered" row. This must be in the plan, not discovered in the demo.

**Distribution architecture.** Two npm packages (`veil-x402-merchant`, `veil-x402-agent`) published to the public registry, one hosted facilitator, one hosted dashboard. Build/publish via GitHub Actions on free minutes. Included, not deferred, because the submission is judged on a judge being able to integrate without local setup.

**Findings — Section 1: 8 issues (AR1, AR2 critical; AR3, AR5, AR6, AR7 high; AR4, AR8 medium).**

## Section 2: Code Quality Review

Repo is empty; this reviews the plan's proposed structure.

**CQ1 — vocabulary (WARNING).** The plan uses "alias," "one-time deposit address," "derived address," "payment alias," "receiving account," and "derivation index" for related-but-distinct things. One glossary, committed to the plan: **alias** = buyer-scoped public handle registered by the merchant; **payment account** = the one-time pool token account a payment lands in; **derivation index** = the merchant's private address→alias resolver; **pool** = the set of pre-configured payment accounts (AR2).

**CQ2 — shared code, proven callers (CRITICAL).** Two extractions are justified, both with two first-party proposed callers each (permitted in an engineering-plan review, labeled as proposals):
- `@veil/derive` — callers: `merchant-sdk` `resolveAddress()` and `agent-sdk` `derivePaymentAccount()`. Contract: `derivePaymentAccount(merchantAliasPubkey, buyerPubkey, nonce) -> {address, nonce}`. Blast radius of a shared failure: the graph silently leaks (addresses not unlinkable) or payments land unattributable. Covered by a property test.
- `@veil/x402-core` — callers: `merchant-sdk` (builds the 402) and `agent-sdk` (parses it). Contract: `parseRequirements(402Body) -> Requirements`, `assertPrice(Requirements) -> Amount`. Blast radius: merchant and agent disagree on price → serve/reject mismatch.
Both are minimal, single-purpose, and replace duplication rather than adding an option matrix. **Net change grows slightly** because tests and integration are counted; the savings are in prevented drift, which is the real win here.

**CQ3 — cyclomatic complexity (HIGH).** The facilitator `verify()` branches on: pid shape, RPC result, tx found, mint match, extension present, amount plaintext?, amount match, slot freshness, idempotency state, merchant live → ~10 branches. **Remedy:** split into `verifyInclusion`, `assertConfidential`, `assertAmount`, `claimServe` (AR7), each independently testable.

**CQ4 — dependency spine (HIGH).** Every module's imports change with AR1. The plan must pin `@solana-program/token-2022`, `@solana/zk-sdk`, `@solana-program/zk-elgamal-proof`, the x402 SDK, and `@solana/web3.js`; commit the lockfile; and record the WASM requirement of `@solana/zk-sdk` (it constrains the facilitator host and the browser bundle).

**CQ5 — over-engineering (WARNING).** Two settlement paths (confidential and a public fallback) would make every verification branch on both forever. **Remedy:** one enforced path (AR3). The fallback is a test fixture, never a runtime mode.

**CQ6 — under-engineering (HIGH).** No input validation on the 402 body, no price bound, no pre-flight pool/rent check, no retry discipline. Happy-path-only patterns in a payments path. Fold into AR7/CQ3.

## Section 4: Performance Review

**P1 — RPC budget (revised by AR4).** Devnet limits are ~100 req/10s per IP, ~40/10s for a single method. If tx-v1 makes a confidential transfer one confirmation (AR4), the per-payment cost drops from the CEO review's 6-10 calls to roughly: 402 parse (local) + blockhash + send + confirm + facilitator verify reads + assertion reads ≈ 5-8 RPC calls. 50 payments ≈ 250-400 calls. Still needs pacing and a Helius free key, but the headroom is better than the CEO review assumed. **Remedy:** measure the actual per-payment call count on day 1, publish it, and pace the harness.

**P2 — proof generation latency is the demo's runtime floor.** The helper builds proofs, but proof time is still unmeasured and sets how long 50 payments take. If a proof is seconds, the "50 payments" demo is a minutes-long video. **Remedy:** measure on day 1; design the demo around the real number.

**P3 — pool warm-up moves cost out of the hot path (AR2).** Pre-creating and pre-configuring N payment accounts is a one-time, off-camera cost. N must be ≥ the demo's payment count plus recycle headroom; if the pool is exhausted mid-take, the demo stalls. **Remedy:** size the pool at 1.5x the demo payment count, pre-warm before recording, and assert `accounts_open` before the run.

**P4 — dashboard N+1.** Reading each payment's account state in a loop multiplies RPC calls by ledger size. **Remedy:** batch reads; cache decrypted totals.

**P5 — cold start sits inside the agent's request timeout.** A serverless facilitator cold start exceeding the x402 client timeout turns a successful payment into a perceived failure, which is a double-charge vector. **Remedy:** keep the facilitator warm for the demo window or use a long-lived free host; probe on day 1 (CEO review A3).

**Findings — Section 4: 5 issues (P1 revised, P2-P5 confirmed).**
