The 402 body

An agent that has never seen Veil still understands this response, because it is a standard x402 Payment Required body with one added requirement: settle confidentially, or do not settle at all. Every body on this page was captured from a running Veil server — the same process that produced the merchant ledger — and its /.well-known/veil published privacySource: pool-ledger.

the price is public to the payer accepts[0].scheme the on-chain amount is not

Note what is not hidden here, on purpose: the price. An x402 challenge has to state what it costs, and Veil does not pretend otherwise. What stays unreadable is the on-chain amount and the balance either side of it — so the chain records that a confidential transfer happened without recording the figure, while the payer's own HTTP exchange is a private conversation with the server.

The accepts[] entry is a conformant x402 offer. Everything under extra is Veil's addition, and it is published in both directions: hides and exposes name what stays private and what does not, so a client cannot read the privacy claim and miss the boundary. A client that ignores scheme is refused rather than served in the clear.

Every refusal is a specific code

A facilitator that fails opaquely is a support burden and a privacy hole: the agent retries, and a looser code path settles in public. Each failure mode below has one code, one cause and one thing the agent should do.

Veil's confidential-precondition refusals, read from a running server's /.well-known/veil. None of them degrade to a public settlement, and none of them are recoverable by retrying the same request unchanged.
Code HTTP Cause The agent should
VEIL-CONF-001 — Mint is not confidential Do not pay. Fix the configuration, then retry.
VEIL-CONF-002 — Destination cannot receive confidential credits Do not pay. Fix the configuration, then retry.
VEIL-CONF-003 402 Confidentiality cannot be guaranteed — refusing to serve Do not pay. Fix the configuration, then retry. observed: no precondition probe configured
VEIL-CONF-004 402 Buyer spend cap exceeded Backoff, or refill the pool. Never fall back to a plain transfer. observed: spend cap exceeded while quoting
VEIL-CONF-005 503 One-time address pool exhausted Backoff, or refill the pool. Never fall back to a plain transfer. observed: pool exhausted while quoting

The proofs are generated in this browser

"Private" means nothing if a server does the proving, because then the server learns every amount. So this is not a claim on a slide: press the button and this page builds the three zero-knowledge proofs a confidential transfer needs, from the payer's own keys, on this device. It also counts the network requests made while it works, so you do not have to take "no prover service" on trust.

The signal a merchant actually ships

Everything above is produced by a facilitator the merchant points at. From the merchant's side the change is one value in the settlement config; the response body does the rest. The refusal below is real output from a running server — the same code the merchant dashboard renders as a row with no amount beside it.

before · plain x402settles in the open
